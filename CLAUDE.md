# Pixhull

Браузерный инструмент: пиксель-арт объекта с шести сторон → воксельная модель →
пиксель-точные спрайтовые повороты, `.obj`, `.glb`, `.vox`. Бесплатный, MIT,
открытый; работает целиком в браузере на GitHub Pages, без сервера и установки.
Для пиксель-художников и разработчиков игр. Живёт на
<https://metalismaticus.github.io/Pixhull/>.

## Стек

- **Чистые ES-модули, без зависимостей и без шага сборки.** Нет `package.json`,
  нет `node_modules`. Браузер получает те же файлы, что лежат в репозитории.
- **WebGL2** — вывод модели инстансингом граней (`src/gfx/renderer.js`).
- **Node 22** — только для инструментов и MCP-сервера (`tools/`, `mcp/`);
  в продукте Node не участвует.
- **Цели:** настольные браузеры с WebGL2. Телефон не цель.
- **Публикация:** GitHub Pages из ветки `gh-pages`, зеркало `main`.

## Каталоги

```
index.html      приложение целиком, одна страница
download.html   страница локального приложения и инструкции MCP
css/app.css     единственный стиль; все цвета — переменными в :root
src/core/       ядро без DOM: виды, карвинг, объём, палитра, поле плотности
src/gfx/        WebGL2: рендерер, камера
src/edit/       редактор: выбор вокселя, инструменты, история
src/export/     спрайты, OBJ, glTF, .vox, surface nets, zip
src/ui/         декодирование картинок, тема
mcp/            MCP-сервер на stdio: тот же карвинг из Node
tools/          check.mjs, mcp-smoke.mjs, serve.mjs
assets/         иконки
docs/           документация проекта
docs/orders     виды заказов: стиль, постоянная часть промта, формат, исполнитель
docs/prompts    готовые заказы по партиям
```

## Запуск и проверка

```bash
node tools/serve.mjs 5173     # продукт: http://localhost:5173
node tools/check.mjs          # быстрая: импортирует все 30 модулей
node tools/mcp-smoke.mjs      # сквозной прогон MCP: карвинг и все экспорты
```

`check.mjs` — вердикт честный: при синтаксической ошибке в модуле возвращает 1
(проверено намеренной поломкой). `mcp-smoke.mjs` возвращает 1, когда сам видит
провал, **но его проверки поверхностные**: он смотрит, что файл создан и
правдоподобного размера, а не что внутри правильно — испорченный заголовок
`.vox` он пропускает. Полная таблица и оговорки — `docs/TESTING.md`.

## Команды

| Команда | Чат | Когда звать |
|---|---|---|
| `/idea <заметка или список>` | замысла | разобрать идеи, баги и вопросы, объединить повторы, проверить факты и дождаться подтверждения; код не писать |
| `/bug <симптом>` | замысла | что-то сломалось — записать в BUGS, причину предложить, но не чинить |
| `/order <вид> <что>` | замысла | нужен арт, музыка, звук, макет, текст — собрать заказ по `docs/orders/<вид>.md`, записать долг, отправить исполнителю, если он автоматический. `/art`, `/music`, `/design` — короткие формы |
| `/need [раздел]` | замысла | показать все долги владельца с готовыми промтами; ничего не правит |
| `/board` | любой | один экран: очередь, партия, долги, баги; ничего не правит |
| `/start [пункт\|all]` | разработки | выполнить первый пункт очереди, названный пункт или всю доступную очередь; каждый одобренный шаг — контрольный коммит |
| `/done [кроме\|только ...]` | разработки | владелец проверил результат — принять партию или её часть, непринятое откатить |
| `/add [папка]` | разработки | разобрать пришедшие файлы заказов: узнать, проверить, записать |
| `/check [имя]` | разработки | прогнать проверки и разобрать провалы |
| `/retro` | разработки | после `/done`: что в партии пошло не так и что из этого урок проекта, а что — процесса |

## Какой документ когда

| Документ | Про что | Когда открывать |
|---|---|---|
| `docs/CONCEPT.md` | что за продукт, что работает, как устроено | перед любой правкой поведения |
| `docs/ROADMAP.md` | сделано / очередь / дальше | когда решаем, что делать следующим |
| `docs/BUGS.md` | только сломанное для пользователя | нашли дефект; закрыли — удалили запись |
| `docs/BLOCKED.md` | долги владельца: заказы и решения | ждём чего-то не от кода |
| `docs/DECISIONS.md` | почему сделано так, а не иначе | тянет переделать — сначала сюда |
| `docs/TESTING.md` | как проверяется работоспособность | перед проверкой и перед коммитом |
| `docs/DESIGN.md` | правила интерфейса: сетка, типографика, состояния | любой пункт с меткой `[ui]` |
| `docs/orders/` | виды заказов | любой заказ: `/order`, `/need`, `/add` |
| `docs/prompts/` | готовые заказы по партиям | `/order`, `/need` |
| `docs/specs/` | спецификации экранов от `designer` | пункты `[ui]` |
| `docs/BATCH.md` | текущая партия чата разработки | `/start`, `/done` |

## Два чата

Замысел и разработка ведутся в разных чатах, но в одной папке и на одной ветке
`main`. Разделяет их не папка, а то, что каждый трогает:

| | Чат замысла | Чат разработки |
|---|---|---|
| команды | `/idea`, `/bug`, `/order`, `/need` | `/start`, `/done`, `/add`, `/check`, `/retro` |
| что меняет | только `.md`: документы, заказы | код, данные, ассеты, проверки, `docs/BATCH.md` |
| продукт | не запускает никогда: причину ищет по коду, замер отдаёт в очередь | запускает и меряет — руками субагентов |
| коммиты | свои `.md` — сразу в `main` | каждый зелёный пункт — сразу в `main` |

Рабочей ветки нет намеренно. У папки одна текущая ветка: уйди чат разработки в
свою — коммиты чата замысла легли бы туда же. Поэтому контрольные коммиты идут
прямо в `main`, а непринятое `/done` откатывает revert-коммитом.

Порядок держат правила:

- каждый коммитит только свои файлы и называет их поимённо — никогда
  `git add -A` или `git add .`;
- во время партии чат разработки из документов правит только `docs/BATCH.md`,
  остальные — при `/done`. Идеи, внесённые в очередь во время партии, ждут
  следующей: `/start all` снимает очередь один раз;
- пришедшее `/add` в очередь не ставит: строки для `ROADMAP.md` и `BLOCKED.md`
  он пишет в раздел «Пришло — внести в очередь» файла `docs/BATCH.md`, а
  переносит их и выбирает место чат замысла;
- чат разработки — тот, где звали `/start`; в любом другом «делай» разработку
  не запускает.

## Как приходит работа

Сообщение через `/idea` — всегда разбор: показать владельцу, как поняты пункты,
и перенести в документы только после подтверждения. Даже слово «сделай» внутри
такого сообщения не разрешает начинать реализацию.

Список в обычном сообщении — **не наряд на работу**. Каждый пункт сначала
уходит туда, где ему место:

| Что прислали | Куда |
|---|---|
| сломано у пользователя | `docs/BUGS.md` — симптом, причина, чем подтверждена |
| новая функция или переделка | `docs/ROADMAP.md`, разбитое на куски |
| про замысел продукта | `docs/CONCEPT.md` |
| нужен заказ или решение | `docs/BLOCKED.md` |
| пришёл файл заказа | `/add` в чате разработки |

Общая очередь выстраивается **сама** в `docs/ROADMAP.md` — это работа чата, а
не вопрос к владельцу. В ней вперемешку стоят ссылки на баги и пункты
разработки: `BUGS.md` хранит подробности дефекта, `ROADMAP.md` определяет его
место среди всей работы. Описание в оба файла не копировать.

Приоритет — по совокупности, а не по ярлыку «баг»:

1. пользователь не может пользоваться продуктом, теряет данные или управление;
2. скольких и как часто задевает проблема;
3. что разблокирует другие пункты;
4. подтверждено ли поведение замером;
5. стоимость работы — только после влияния и уверенности.

Пункт, которому нужен ответ, файл или проверка владельца, остаётся в очереди с
пометкой `ждёт` и пропускается при автоматическом выполнении.

В чате разработки обычное **«делай»** равно `/start`, **«делай всё»** — `/start
all`. Спрашивать «с чего начать?» не нужно: ответ следует из очереди.
Спрашивать нужно другое — **чего в продукте ещё нет**: замысел, числа,
названия, судьба спорной функции.

## Метки пунктов очереди

Состояние: `[можно]` — бери; `[ждёт …]` — нужен ответ, файл или проверка
владельца. Маршрут:

| Метка | Кто делает |
|---|---|
| `[код]`, `[баг]` | `executor` → `reviewer` с полной проверкой |
| `[ui]` | `designer` пишет спецификацию экрана → `executor` → `reviewer` со снимками |
| `[данные]` | `executor` → `reviewer` с проверкой пункта и быстрой проверкой, без полной |

## Правила проекта

- **Ни одной зависимости и ни одного шага сборки.** Pages отдаёт исходники как
  есть; всё, что нужно браузеру, лежит в репозитории готовым. Чужой код можно
  только вписать своими руками и только под совместимой лицензией — см.
  `docs/DECISIONS.md`.
- **Ядро не знает про DOM.** `src/core/` работает одинаково в браузере и в Node
  (`mcp/`): картинка приходит как `{width, height, data}` в RGBA8. Одна
  реализация карвинга, а не две, которые должны совпадать.
- **Всё содержимое репозитория — на английском:** код, комментарии, сообщения
  коммитов, README, строки интерфейса. Русский — только в `README.ru.md` и в
  `docs/` процесса.
- **Каждая строка интерфейса — через `src/i18n.js`, в двух языках сразу.**
  Ключ, добавленный в EN и забытый в RU, — это дефект; счётчик ключей обязан
  совпадать.
- **Байт грани — источник истины.** Грань хранит индекс палитры; менять
  *значение* индекса можно (это загрузка текстуры 256×1), перенумеровывать
  индексы — нельзя: это обнулит смысл каждого байта в объёме и в истории правок.
- **Проверять замером, а не рассуждением.** В этом проекте каждый найденный
  дефект был найден числом, и каждое «это свойство метода, а не баг» дважды
  оказывалось багом. Вывод из кода — гипотеза, пока её не подтвердил прогон.

## Правила процесса

- **Проверять замером, а не рассуждением.** Вывод из кода — ещё не проверка.
- **Заказное — заказом, а не кодом.** Картинки, музыка, звук, макеты идут
  через `/order`. Перед заказом сверить, не лежит ли уже готовое.
- **Чат разработки — координатор.** Пункт делает свежий субагент `executor`,
  до коммита его проверяет свежий `reviewer`, не больше трёх кругов; основной
  чат кода не пишет и логов не копит.
- **Зелёный шаг `/start` — контрольный коммит и push.** Это точка сохранения, а
  не принятие результата. Push идёт в `main` и зеркалом в `gh-pages`, откуда
  публикуется Pages.
- **Только `/done` после проверки владельцем принимает работу.** Непринятое
  откатывается revert-коммитом. Красный шаг не коммитить.
- **Пока в `docs/TESTING.md` состояние полигона не «есть»**, одобрение
  `reviewer` значит только «запускается без ошибок» — и он обязан так и писать.
