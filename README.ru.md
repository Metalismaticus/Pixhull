# Pixhull — инструкция на русском

> Перевод [README.md](README.md). Код, коммиты и комментарии в репозитории —
> на английском; этот файл существует только как документация.

**[Открыть приложение &rarr;](https://metalismaticus.github.io/Pixhull/)** &nbsp;·&nbsp;
[Запустить локально](https://metalismaticus.github.io/Pixhull/download.html)

Превращает пиксель-арт в ортографических проекциях (вид спереди / сбоку /
сверху) в 3D воксельную модель, а затем экспортирует pixel-perfect спрайтовые
обороты и OBJ-модели.

Работает целиком в браузере. Без установки, без аккаунта, без сервера, без
шага сборки. Бесплатно и с открытым исходным кодом.

---

## Что это делает

Загружаете до шести ортографических изображений — спереди, сзади, слева,
справа, сверху, снизу — и Pixhull пересекает их силуэты в воксельную модель,
переносит пиксели каждого вида на те грани, которые этот вид видит, и рендерит
результат ортографической камерой, привязанной к пиксельной сетке.

```
front.png ─┐
side.png  ─┼─►  визуальная оболочка ─► цвет на грани ─► ┬─► спрайт-лист + JSON
top.png   ─┘                                            └─► OBJ + MTL
```

### Шесть цветов на воксель, а не один

Воксель хранит независимый индекс палитры для каждой из шести граней. Спереди
вы видите пиксель вида спереди, сбоку — пиксель вида сбоку. Именно поэтому
результат читается как исходный арт, а не как его кубическое приближение — и
именно поэтому `.vox` здесь не является родным форматом (в MagicaVoxel воксель
несёт один цвет).

### Углы, которые ложатся на пиксельную сетку

Если шагать оборот по `360/n` градусов, получаются углы, у которых спроецированные
рёбра имеют иррациональный наклон. Ребро куба под 22.5° не может лечь на
пиксельную сетку, поэтому каждому кадру нужно сглаживание — а сглаживание как раз
и убивает ощущение пиксель-арта.

Pixhull вместо этого генерирует углы из дерева Штерна — Броко, так что каждое
ребро превращается в повторяющуюся пиксельную лесенку:

| направлений | равномерно `360/n`        | pixel-clean                        |
|------------:|---------------------------|------------------------------------|
| 8           | 0, 45, 90, 135, …         | 0, 45, 90, 135, … (уже чистые)     |
| 16          | 0, **22.5**, 45, **67.5** | 0, **26.565** (1:2), 45, **63.435** (2:1) |
| 12          | 0, 30, 60, 90, …          | 0, 30.964 (3:5), 59.036 (5:3), 90, … |

Работает любое число кадров от 1 до 64. Значения, не равные `4·2^k`, получают
равномерные углы, примагниченные к ближайшему чистому наклону.

### Экспорт, который не «плывёт»

Каждый кадр оборота использует **один размер холста и записанный пивот**. Размер
кадра вычисляется один раз как наибольшая проекция по всем углам, а модель
центрируется по целому пикселю — поэтому ничего не дрожит при повороте и ничего
не съезжает на пиксель, когда спрайты попадают в движок. Покадровой автообрезки
нет в принципе.

Рядом со спрайт-листом кладётся `sprites.json` с размером кадра, углом каждого
кадра, смещениями в листе, пивотами и палитрой.

### Палитра гарантирована по построению

Цвета при импорте попадают в индексированную палитру на 255 записей. Модель не
может содержать цвет, которого не было в исходном арте; рендер идёт с выключенным
сглаживанием; затенённый экспорт примагничивается обратно к палитре. Плоский
экспорт проверяемо точен: ноль пикселей вне палитры, ноль полупрозрачных.

### Зеркальная заливка для видов, которые вы не рисовали

Если нарисованы три вида, то у трёх направлений источника нет вовсе — сзади,
слева и снизу. Подбор цвета по соседним граням оставляет половину модели плоской
и неправильной, а грань вообще без цвета *отбрасывается шейдером* — и это
сквозная дыра, через которую видно фон.

Поэтому недостающий вид достраивается зеркалированием противоположного. Форму это
изменить не может: силуэт сзади у непрозрачного объекта и есть зеркальный силуэт
спереди, так что зеркальный вид добавляет только цвет. Всё, что осталось не
покрытым, заливается доминирующим цветом модели. Инвариант: ни одна открытая
грань никогда не остаётся без цвета.

### Светлая и тёмная тема, английский и русский

Обе темы при первом запуске берутся из системных настроек и дальше запоминаются.
Язык интерфейса переключается в верхней панели — вместе с форматом чисел,
который подстраивается под локаль.

### Редактирование — без него метод неполон

Визуальная оболочка не может воспроизвести вогнутость, которую не выдаёт ни один
силуэт, поэтому ручное редактирование здесь не довесок, а вторая половина метода.
Красьте грань или воксель целиком, заливайте поверхность ведром (заливка идёт по
лесенкам, а не останавливается на краю плоскости), стирайте, добавляйте, снимайте
цвет пипеткой. Кисть до 9³, зеркалирование по X, отмена и возврат, где **один
мазок — один шаг**, а не один воксель.

Любая операция, которая может открыть новую грань, тут же её закрашивает: грань
без цвета отбрасывается шейдером и превращается в дыру.

Проект сохраняет воксели, а не только исходные виды — пересборка из тех же PNG
никогда не воспроизвела бы вырезанное руками. Два RLE-потока ужимают демо с 94 КиБ
до 5,8 КиБ, и обратное чтение побитово совпадает с исходным.

### Экспорт в мир, где у вокселя один цвет

В `.vox` у вокселя один цвет, а в Pixhull их шесть. Экспорт решает это
голосованием среди граней, которые реально видно: покрышка, у которой все
видимые грани чёрные, остаётся чёрной, а закрытые грани права голоса не имеют —
иначе скрытая геометрия начинает определять внешний вид модели. Палитра на 256
записей совпадает с нашей один в один, так что цвета переносятся без
переквантования.

### Гладкие меши, а не только кубики

Вырезание идёт по решётке и иначе не будет — это свойство метода, и размер сетки
задаёт, сколько вообще есть деталей. Но экспортируемый *меш* кубическим быть не
обязан. Включите «гладкий меш», и OBJ соберётся через surface nets, **и окно
покажет то же самое**: по одной
вершине на каждую ячейку, которую пересекает поверхность, в среднем положении
пересечений рёбер — лесенка превращается в округлую low-poly оболочку. Ползунок
скругления добавляет сверху лапласовы проходы.

Цвет при таком переводе достаётся бесплатно: квад для ребра между полным и
пустым вокселем — это ровно та грань, которую Pixhull уже покрасил. То есть
сглаживание стоит детализации геометрии и никогда не стоит цвета. Демо выходит
замкнутым многообразием: 1084 квада, 1086 вершин, каждое ребро использовано
ровно дважды. Полигонов больше, чем у кубического экспорта со склейкой (98
квадов), потому что surface nets не объединяет компланарные грани.

### Управление из ассистента

Рядом с приложением лежит MCP-сервер — [`mcp/`](mcp/README.md). Указываете
ассистенту папку с PNG, и он может собрать модель, **посмотреть на то, что
получилось**, и выгрузить OBJ, `.vox` или спрайт-лист. Локально, через файлы
на диске, без хостинга и без аккаунта.

Он гоняет те же модули, что и страница, а не их порт, поэтому разойтись они не
могут: из одних и тех же трёх PNG оба дают 1438 вокселей и кадры 25×20. WebGL
в Node нет, так что превью рисуется на CPU — по лучу на пиксель через тот же
обход сетки, которым редактор ловит клики. Камера ортографическая, геометрия
сеточная, поэтому результат совпадает с тем, что дал бы GPU.

Зависимостей там тоже нет: декодирование PNG опирается на встроенный в Node
zlib, а протокол — JSON-RPC по stdio, написанный напрямую.
### Один лист на входе, виды на выходе

У художника обычно лежит один PNG, где вид спереди, сбоку и сверху нарисованы
рядом, а не три аккуратных файла. Загрузите его, и Pixhull найдёт рисунки по
пустым промежуткам — не по связным компонентам, которые раскрошили бы персонажа
с отдельно стоящими конечностями, а по полосам прозрачных строк и столбцов,
потому что именно это человек и имеет в виду под «здесь разные рисунки».

Дальше он определяет, что есть что, по размерам: ортографические виды обязаны
сходиться по общим осям — спереди и справа одной высоты, сверху той же ширины,
что спереди, и той же глубины, что ширина вида справа. Обычно всем трём
условиям отвечает ровно одна расстановка, и тогда он так и говорит; иначе —
порядок чтения, а вы поправите в один клик. Модель из нарезанного листа
совпадает с моделью из трёх отдельных файлов воксель в воксель.
### glTF — для движков, которым 255 материалов ни к чему

OBJ читают все, но он приезжает с отдельным материалом на каждый цвет палитры,
и разгребать это неприятно. В `.glb` цвет лежит вершинным атрибутом, поэтому
модель — это один материал и один вызов отрисовки, а Godot, Unity и Unreal
импортируют её без плагинов.

Вершины между гранями намеренно не переиспользуются: угол вокселя принадлежит
граням разных цветов, и усреднение размазало бы палитру ровно по тем рёбрам, на
которых арт и держится. `KHR_materials_unlit` объявлено как используемое, но не
обязательное: кто его понимает — покажет палитру точно, кто нет — всё равно
отрисует верно.
### Арт крупнее сетки уменьшается, а не обрезается

Лист, нарисованный шириной в 450 пикселей, — это не пиксель-арт в масштабе
вокселя, и его надо привести к сетке. Каждая ячейка берёт коробку исходных
пикселей: полная, если полна большая часть коробки, и красится самым частым её
цветом. Точечная выборка была бы дешевле и неверна дважды — она теряет тонкие
детали вроде кромки крыла и цепляет пиксели сглаживания, не принадлежащие ни
одной стороне контура.

При уменьшении виды заодно согласуются между собой. Рисованные листы сплошь и
рядом расходятся по общей оси — вид сбоку нарисован на 18% ниже, чем говорит
вид спереди. Ортографический силуэт по определению занимает всю протяжённость
модели по обеим своим осям, так что подгонка каждого вида к согласованной
протяжённости — это исправление, а не подгонка под ответ. В строке состояния
называется вид, который пришлось растянуть сильнее всех.

Арт, который и так помещается в сетку, не трогается вовсе: один пиксель на
воксель и целые смещения. Пересэмплировать крыло из 12 пикселей в 13 ячеек —
значит дорисовать столбец, которого художник не рисовал. Проверено в обе
стороны: демо по-прежнему даёт 1438 вокселей, а согласованный арт, увеличенный
в 8 или 37 раз и уменьшенный обратно, вырезает ту же самую модель.
### Когда лист не может сработать — инструмент скажет

Shape-from-silhouette проваливается молча и дорого. Положите в слот «спереди»
рисунок, который на самом деле второй вид сверху, — карвинг всё равно
отработает, всё равно сообщит число вокселей и вернёт монолитный мусор. В
цифрах не будет ни намёка на причину, и естественный вывод — что сломан
инструмент.

Но это проверяемо. Виды с разными парами осей не должны быть похожи: «спереди»
занимает (x, y), «сверху» — (x, z). Если их силуэты совпадают, значит один и тот
же рисунок стоит в двух слотах. Противоположные виды совпадать обязаны и из
проверки исключены. Каждый силуэт сначала приводится к штампу 32×32 по
собственной рамке, чтобы положение не замаскировало совпадение.

Пропорции же работают не маскировкой, а воротами: пара называется, только
если оба рисунка почти одинаковых пропорций — в пределах
`PROPORTION_TOLERANCE = 1.15`. Две настоящие проекции одного объекта такими
бывают редко, а один и тот же рисунок в двух слотах — всегда. Эти ворота и
держат встроенное демо молчаливым: пара «спереди / справа» даёт 0.81 по форме
и 1.92 по пропорции.

На настоящем листе, где нижние два рисунка оказались парадными ракурсами, а не
проекциями, «сверху» против «спереди» дало 0.79, «сверху» против «сзади» — 0.81,
против 0.52 у настоящего вида сбоку. Строка состояния теперь называет пару.
Известная цена: смешанная пара — один парадный ракурс против настоящей
проекции — в ворота пропорций не проходит и отбрасывается молча.
### Палитра набирается по площади, а не по очереди

Раньше цвета попадали в палитру в порядке встречи — из-за этого белый фургон
выходил целиком серым: кузов с антиалиасингом давал сотни почти одинаковых
оттенков серого, они занимали все 255 мест, и красная кабина, встреченная
позже, примагничивалась к ближайшему из уже имеющихся, то есть к серому.
Теперь сначала опрашиваются все виды, а палитра набирается цветами, которые
покрывают наибольшую площадь: настоящая палитра попадает в таблицу, а
бахрома сглаживания ложится на неё.

### Виды, нарисованные лёжа

Художник кладёт вид сверху вдоль, чтобы сэкономить место на листе, и по
горизонтали у него оказывается длина модели там, где инструмент ждёт ширину.
Масштабированием это не лечится: на фургоне потребовалось бы растяжение в
2.07×, и результат всё равно был бы неверным. Теперь каждый вид можно
повернуть на четверть, а подгонка сама подбирает повороты так, чтобы общие оси
сошлись — перебором всех 64 сочетаний, потому что шесть видов не требуют
хитростей. Фургону это снизило растяжение с 2.07× до 1.26×. Повёрнутый вручную
вид дальше не трогается.
### Как повёрнут каждый рисунок

Совпадения размеров недостаточно. Вид сверху, положенный вдоль, одинаково
хорошо ложится в сетку повёрнутым по часовой и против, так что солвер, который
сравнивает только габариты, выбирает произвольно — и в половине случаев нос
оказывается не с того конца модели. Тогда вид спереди красит корму, а всюду,
где два рисунка расходятся в том, где кончается кабина, грань красится не с той
стороны: красные пятна на белом кузове, белые полосы по красной кабине. Одна
ошибка ориентации — оба симптома.

Решают два рода свидетельств. Виды с общей осью смотрят вдоль неё на один и тот
же объект, значит их профили заполненности вдоль этой оси обязаны совпадать —
это ловит зеркальность. Но закрепить ось в пространстве так нельзя: разверните
Z сразу во всех видах, и все профили по-прежнему сойдутся, а модель будет
собрана задом наперёд. Якорь в другом: **дальний срез вида вдоль оси должен
быть похож на тот вид, который смотрит вдоль этой оси**. Нос на виде сбоку
обязан быть цвета вида спереди. На фургоне с красной кабиной это решает всё.

При шести видах и четырёх оставшихся ориентациях перебор полный. Жадный проход
был написан первым и провалился ровно там, где и ожидалось: ему приходилось
выбирать ориентацию бокового вида раньше, чем поставлен хоть один вид вдоль его
длинной оси, — сравнивать было не с чем.

На листе с фургоном он поворачивает вид сверху на 270°, а не на 90°, и зеркалит
оба боковых — то же, к чему приходит человек вручную. Красные грани из
размазанных по всей длине собираются на 89% в последнюю четверть.
### Любые размеры изображений

Виды не обязаны быть квадратными, не обязаны совпадать друг с другом и не обязаны
быть степенью двойки. Каждый вид обрезается по содержимому и размещается на сетке
независимо. В демо намеренно использованы 12×12, 24×12 и 12×24.

## Запуск локально

ES-модули не грузятся по `file://`, поэтому нужен локальный сервер — он есть
в комплекте:

```bash
node tools/serve.mjs
```

Дальше откройте <http://localhost:5173>. Никакого `npm install` — зависимостей нет.

Проверить, что все модули парсятся:

```bash
node tools/check.mjs
```

Он импортирует каждый модуль, а не зовёт `node --check` — тот однажды пропустил
строковый литерал, разорванный переводом строки, который браузер отверг сразу.

Проверить MCP-сервер целиком:

```bash
node tools/mcp-smoke.mjs
```

отдаёт Pages. Собирать нечего: корень репозитория и есть сайт.

### Известные ограничения подхода

Визуальная оболочка принципиально не может воспроизвести вогнутость, которую не
выдаёт ни один силуэт — внутреннюю часть капюшона, вмятину, глухое отверстие. Они
получаются заполненными. Две несвязанные формы на разных видах также порождают
фантомный объём там, где их проекции пересекаются. И то и другое — свойство
метода shape-from-silhouette, а не баг; и именно поэтому редактор здесь
обязателен, а не опционален.
