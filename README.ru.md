# Pixhull — инструкция на русском

> Перевод [README.md](README.md). Код, коммиты и комментарии в репозитории —
> на английском; этот файл существует только как документация.

**[Открыть приложение &rarr;](https://metalismaticus.github.io/Pixhull/)**

Превращает пиксель-арт в ортографических проекциях (вид спереди / сбоку /
сверху) в 3D воксельную модель, а затем экспортирует pixel-perfect спрайтовые
обороты и OBJ-модели.

Работает целиком в браузере. Без установки, без аккаунта, без сервера, без
шага сборки. Бесплатно и с открытым исходным кодом.

---

## Что это делает

Загружаете до шести ортографических изображений — спереди, сзади, слева,
справа, сверху, снизу — и Pixhull пересекает их силуэты в воксельную модель,
переносит пиксели каждого вида на те грани, которые этот вид видит, и рендерит
результат ортографической камерой, привязанной к пиксельной сетке.

```
front.png ─┐
side.png  ─┼─►  визуальная оболочка ─► цвет на грани ─► ┬─► спрайт-лист + JSON
top.png   ─┘                                            └─► OBJ + MTL
```

### Шесть цветов на воксель, а не один

Воксель хранит независимый индекс палитры для каждой из шести граней. Спереди
вы видите пиксель вида спереди, сбоку — пиксель вида сбоку. Именно поэтому
результат читается как исходный арт, а не как его кубическое приближение — и
именно поэтому `.vox` здесь не является родным форматом (в MagicaVoxel воксель
несёт один цвет).

### Углы, которые ложатся на пиксельную сетку

Если шагать оборот по `360/n` градусов, получаются углы, у которых спроецированные
рёбра имеют иррациональный наклон. Ребро куба под 22.5° не может лечь на
пиксельную сетку, поэтому каждому кадру нужно сглаживание — а сглаживание как раз
и убивает ощущение пиксель-арта.

Pixhull вместо этого генерирует углы из дерева Штерна — Броко, так что каждое
ребро превращается в повторяющуюся пиксельную лесенку:

| направлений | равномерно `360/n`        | pixel-clean                        |
|------------:|---------------------------|------------------------------------|
| 8           | 0, 45, 90, 135, …         | 0, 45, 90, 135, … (уже чистые)     |
| 16          | 0, **22.5**, 45, **67.5** | 0, **26.565** (1:2), 45, **63.435** (2:1) |
| 12          | 0, 30, 60, 90, …          | 0, 30.964 (3:5), 59.036 (5:3), 90, … |

Работает любое число кадров от 1 до 64. Значения, не равные `4·2^k`, получают
равномерные углы, примагниченные к ближайшему чистому наклону.

### Экспорт, который не «плывёт»

Каждый кадр оборота использует **один размер холста и записанный пивот**. Размер
кадра вычисляется один раз как наибольшая проекция по всем углам, а модель
центрируется по целому пикселю — поэтому ничего не дрожит при повороте и ничего
не съезжает на пиксель, когда спрайты попадают в движок. Покадровой автообрезки
нет в принципе.

Рядом со спрайт-листом кладётся `sprites.json` с размером кадра, углом каждого
кадра, смещениями в листе, пивотами и палитрой.

### Палитра гарантирована по построению

Цвета при импорте попадают в индексированную палитру на 255 записей. Модель не
может содержать цвет, которого не было в исходном арте; рендер идёт с выключенным
сглаживанием; затенённый экспорт примагничивается обратно к палитре. Плоский
экспорт проверяемо точен: ноль пикселей вне палитры, ноль полупрозрачных.

### Любые размеры изображений

Виды не обязаны быть квадратными, не обязаны совпадать друг с другом и не обязаны
быть степенью двойки. Каждый вид обрезается по содержимому и размещается на сетке
независимо. В демо намеренно использованы 12×12, 24×12 и 12×24.

## Управление

| Действие | Как |
|----------|-----|
| Загрузить вид | Перетащите PNG на слот, или кликните по слоту |
| Вращать камеру | Зажать левую кнопку мыши и тянуть |
| Панорамировать | Средняя кнопка, либо Shift/Ctrl + тянуть |
| Зум | Колесо мыши (целые шаги, иначе пиксели «мылятся») |
| Фикс. ракурсы | Кнопки Front / Right / Back / Left / Iso, либо клавиши 1–5 |
| Отразить вид | Кнопки H и V на слоте |

## Запуск локально

ES-модули не грузятся по `file://`, поэтому нужен локальный сервер — он есть
в комплекте:

```bash
node tools/serve.mjs
```

Дальше откройте <http://localhost:5173>. Никакого `npm install` — зависимостей нет.

## Деплой

Пуш в `main`. Приложенный workflow зеркалит его в `gh-pages` — именно эту ветку
отдаёт Pages. Собирать нечего: корень репозитория и есть сайт.

## Как это устроено

| Файл | Что там |
|------|---------|
| [`src/core/volume.js`](src/core/volume.js) | Разреженное воксельное хранилище чанками 16³: битсет занятости + 6 байт палитры на воксель |
| [`src/core/carve.js`](src/core/carve.js) | Пересечение силуэтов и перенос цвета на грани |
| [`src/core/views.js`](src/core/views.js) | Исходные изображения, обрезка, размещение, соглашение «вид ↔ оси» |
| [`src/gfx/camera.js`](src/gfx/camera.js) | Ортографическая камера и математика pixel-clean углов |
| [`src/gfx/renderer.js`](src/gfx/renderer.js) | Инстансированный рендер граней — один draw call на всю модель |
| [`src/export/sprite.js`](src/export/sprite.js) | Рендер оборота, упаковка листа, примагничивание к палитре |
| [`src/export/obj.js`](src/export/obj.js) | OBJ + MTL с greedy-склейкой граней (~90% меньше квадов на демо) |

### Известные ограничения подхода

Визуальная оболочка принципиально не может воспроизвести вогнутость, которую не
выдаёт ни один силуэт — внутреннюю часть капюшона, вмятину, глухое отверстие. Они
получаются заполненными. Две несвязанные формы на разных видах также порождают
фантомный объём там, где их проекции пересекаются. И то и другое — свойство
метода shape-from-silhouette, а не баг; и именно поэтому редактирование внутри
приложения стоит в планах как обязательное, а не опциональное.
