# Проверка работоспособности

**Состояние полигона: строится**

Пока состояние не «есть», одобрение `reviewer` значит только то, что названо в
строке «Что проверяется уже сейчас». Он обязан писать это в итоге, а `/start`
— в отчёте владельцу.

## Команды проверки

Единственное место, где записано, **чем** проверять. Команды `/start`, `/done`,
`/check` и субагенты берут их отсюда, а не из памяти.

| Уровень | Команда | Сколько идёт | Как читать вердикт |
|---|---|---|---|
| быстрая — продукт запускается без ошибок | `node tools/check.mjs` | ~2 с | код возврата честный: 1 при сломанном модуле, 0 при чистом (проверено намеренной поломкой `src/core/palette.js`) |
| проверка пункта — одна по имени | нет | | полигона ещё нет — первый пункт очереди |
| группа | нет | | |
| полная | `node tools/check.mjs && node tools/mcp-smoke.mjs` | ~15 с | оба возвращают 1 при провале **своих** проверок; про глубину см. ниже |
| долгая — не входит в полную | нет | | |
| снимок экрана | нет | | делается руками через браузер; автоматизации нет |
| после правки ресурсов | не нужно | | нет шага сборки и нет импорта ассетов |

В контекст чата брать только итоговую строку прогона, а не весь вывод.

**Оговорка про `mcp-smoke.mjs`.** Он возвращает 1, когда сам видит провал
(`tools/mcp-smoke.mjs:239-240`), но его проверки поверхностные: он смотрит, что
файл создан и правдоподобного размера, плюс несколько структурных утверждений о
GLB. Проверено: если испортить чанк `SIZE` в `.vox`, прогон остаётся зелёным.
Читать его как «конвейер отработал и выдал файлы», а не «файлы правильные».

## Данные пользователя

Нет. Продукт ничего не хранит вне вкладки: проект сохраняется файлом, который
владелец скачивает сам. `localStorage` хранит только выбранную тему
(`index.html`, ключ `pixhull.theme`) — потерять там нечего.

Агентам трогать их нельзя. `/start` снимает копию перед партией, которая может
их задеть.

## Полигон

Полигона нет — и это самая дорогая дыра проекта. Каждый дефект, найденный до
`/setup`, ловился одноразовым скриптом-замером, который писали в черновую папку
и выбрасывали. Скрипты выбрасывали, дефекты возвращались.

Полигон должен жить в `tests/` рядом с `tools/`, запускаться `node tests/run.mjs`
(все), `node tests/run.mjs <имя>` (одна), `node tests/run.mjs <группа>/` (группа)
и возвращать 0 / 1 / 2 — зелено / провал / нет такой проверки, с итоговой
строкой «зелёных / провалов».

**Проверки — не на строки кода, а на поведение модели.** Эталон входа —
синтетические картинки, которые рисует сам тест: голый куб, клин под 45°,
ступенька, плавник толщиной в воксель. Такой вход даёт точный ожидаемый ответ,
не тянет за собой чужой арт и не боится смены палитры.

Замеры, которые уже доказали свою полезность и обязаны стать проверками
(написать заново, а не переносить — черновики не сохранились):

| Проверка | Что меряет | Порог, доказанный замером |
|---|---|---|
| `carve/cube-faces` | голый куб с чёрным днищем: ни одна грань не перекрашена видом, который её не видит | ровно 0 из 2400 |
| `carve/slope-banding` | наклонная поверхность: углы, где верхняя и передняя грани спорят друг с другом | было 1623 из 1914, стало 104 |
| `carve/reprojection` | обратная проекция модели через каждый вид против растра рисунка | расхождение по цвету 0 там, где модель есть |
| `carve/visibility` | грань красится только тем видом, который её реально видит | 0 нарушений |
| `views/extent-skew` | перекос пропорций каждого вида относительно самого себя | ≤ 1.03 |
| `views/spike` | спорный выступ стоит там, куда его помещают остальные виды | зеркала на кабине, а не вдоль кузова |
| `i18n/parity` | число ключей EN и RU совпадает | 177 = 177 |
| `perf/carve` | время и пик памяти на 256 / 384 / 512 | 1.1 / 3.7 / 11.0 с, 105 / 175 / 240 МБ |

### Как добавить проверку

1. Файл в `tests/<группа>/<имя>.mjs`, экспортирует `run()` и возвращает
   `{ok, detail}`; `detail` — одна строка с числом, а не с рассуждением.
2. Вход рисуется в самом тесте: `makeFlat(20, 20, [255, 0, 0])` и подобные
   помощники из `tests/fixtures.mjs`.
3. **Правило: новая проверка должна быть красной без исправления и зелёной с
   ним.** Проверить это буквально — откатить исправление и увидеть красное.
   Иначе она ничего не стережёт.
4. Числа-пороги в проверке — из прогона, а не из головы, и рядом комментарий,
   каким прогоном получены.

### Красное, которое бывает правильным

Проверку заводят и на открытый баг — тогда она красная намеренно и стережёт
починку. Прежде чем «чинить красное», сверить с `BUGS.md`. Такую проверку
нельзя убирать или ослаблять ради зелёного итога.

Сейчас такой случай один: остаточная чересполосица на кабине (104 из 1914) —
это открытый дефект, и проверка на него должна быть красной, пока не сделан
photo hull.

### Чего проверки не видят

- **Картинку.** Всё, что про внешний вид модели, ловится только снимком
  экрана. Все дефекты, которые приходили от владельца, были видны глазом и
  невидимы коду: полосы на кабине, белые пятна снизу, двойной ряд фар.
- **Вёрстку интерфейса.** Панели, переносы, тёмная и светлая темы.
- **WebGL.** В Node его нет; рендерер, камера и шейдеры непроверяемы
  автоматически вообще.
- **Поведение браузера** — перетаскивание файлов, скачивание, отклик вкладки
  во время долгой сборки.

## Замеры

Числа снимаются прогоном, а не рассуждением.

- **Время и память карвинга** — скрипт, который строит модель на 256 / 384 /
  512 и печатает миллисекунды, число вокселей, число граней и
  `process.memoryUsage().rss`.
- **Точность цвета** — доля ячеек, где цвет модели совпадает с цветом рисунка,
  при обратной проекции. Именно этот замер показал, что узкое место не сетка, а
  палитра: по сетке 67.9% → 92.4% от 256 к 512, а с учётом палитры лишь
  47.5% → 55.8%.
- **Профиль этапов карвинга** — отдельные времена пересечения, покраски,
  перекраски наклонных и достройки. Им был найден `inferMissingFaces`, евший
  14 из 22 секунд.
- **Кадры в секунду** — в браузере, руками; автоматизации нет и не планируется.
